# Pg Code Verifier 验证规范技能

## 一、核心原则

1. **只验证，不修改**：验证过程中发现问题只报告，不自动修改代码或文档
2. **对照设计文档**：以 `implementation_plan.md`（程序设计文档）为唯一验证基准
3. **结构化输出**：验证结果必须分类输出（✅ 通过 / ⚠️ 待确认 / ❌ 不符合）
4. **引导下一步**：针对每个 ❌ 或 ⚠️ 项，给出具体的修复建议命令

---

## 二、验证维度

### 维度 1：文件完整性验证
对照「涉及文件清单」，检查每个文件是否已产出：

| 文件 | 操作类型 | 状态 |
|---|---|---|
| XxxController.java | 新增 | ✅ 已创建 |
| XxxService.java | 新增 | ❌ 未找到 |
| ApolloConfig.java | 修改 | ✅ 已修改 |

### 维度 2：API 接口一致性验证
对照「API 接口设计」章节，逐项检查：
- 接口路径是否与设计一致（如 `POST /api/xxx/create`）
- 请求参数字段名、类型是否匹配
- 响应结构（code/data/msg 结构）是否符合设计
- 是否向后兼容（有无破坏性变更）

### 维度 3：服务层逻辑一致性验证
对照「服务层核心逻辑」或「时序图」，检查：
- 核心业务逻辑的实现路径是否与设计一致
- 并发/幂等/事务边界是否按设计处理
- 异常处理路径是否覆盖设计中描述的异常场景

### 维度 4：数据模型一致性验证
对照「数据模型变更」章节，检查：
- 新增/修改的字段是否与设计一致（字段名、类型、默认值）
- DO 类的字段变更是否完整

### 维度 5：文档一致性验证
检查代码变更是否与所有文档保持同步：
- 如果接口有变更，程序设计文档中的接口章节是否已更新
- 如果核心逻辑有变更，时序图/流程图是否已更新

## 三、验证报告输出格式

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🔍 验证报告 — [需求名称]
验证时间：YYYY-MM-DD HH:mm
基准文档：[implementation_plan.md 路径]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ XxxController.java — 已创建
❌ XxxService.java — 未找到（设计要求新增）
✅ ApolloConfig.java — 已修改

## 🔌 API 接口一致性
✅ POST /api/xxx/create — 路径、参数、响应均符合设计
⚠️ GET /api/xxx/list — 响应字段 `total` 设计中要求返回但代码中缺失

## ⚙️ 服务层逻辑
✅ 并发场景使用 CompletableFuture — 符合设计
⚠️ 幂等处理：设计要求基于 requestId 去重，代码未见相关实现

## 🗄️ 数据模型
✅ 新增字段 `source_type` — 类型 tinyint，已在 DO 类中添加

## 📝 文档一致性
✅ 代码实现与程序设计文档一致，无需同步

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
验证结论：
✅ 通过：3 项

📋 待处理项目：
1. ❌ XxxService.java 未创建 → `/pg:code` 补充产出该文件
2. ⚠️ GET list 接口缺失 `total` 字段 → `/pg:fix 在 list 接口响应中补充 total 字段`
3. ⚠️ 幂等处理未实现 → 请确认是否需要实现，确认后 `/pg:fix 实现基于 requestId 的幂等去重`
```

## 四、验证后引导规则

| 验证结果 | 引导行为 |
|---|---|
| 全部 ✅ 通过 | 提示可使用 `/pg:done` 进行需求收尾 |
| 有 ⚠️ 待确认 | 列出待确认项，询问用户如何处理，不强制修复 |
| 有 ❌ 不符合 | 明确告知必须修复，给出 `/pg:fix` 命令建议，不允许继续 `/pg:done` |

---

## 五、`/pg:verify` 执行步骤

1. **读取基准文档**：读取 `spec-status.json` 找到 `files.design`，加载程序设计文档
2. **读取代码现状**：扫描「涉及文件清单」中所有文件的实际内容
3. **逐维度验证**：按上述 5 个维度逐一比对
4. **生成报告**：按上述格式输出结构化验证报告
5. **引导下一步**：根据验证结论给出后续操作建议

---

## 六、禁止行为

- ❌ 禁止在验证过程中自动修改任何代码文件
- ❌ 禁止在验证过程中自动修改任何文档文件
- ❌ 禁止忽略任何 ❌ 不符合项直接引导用户 `/pg:done`
- ❌ 禁止模糊报告（如"基本符合"），必须明确标注每一项的状态
