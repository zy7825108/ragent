---
description: PG - 代码审查命令 - 产码完成后对照设计文档和代码质量规范进行 Code Review，输出审查清单与改进建议 (PG Code Review Command)
---

当用户输入 `/pg_review` 命令时，你必须严格按照以下步骤执行：

---

## Code Review 规范（内嵌）

- **只审查，不修改**：发现问题只输出建议，不自动改代码
- **分层审查**：按接口层 → 业务层 → 数据层逐层检查
- **结构化输出**：每个问题标注严重等级（🔴 必须修复 / 🟡 建议修改 / 🟢 可选优化）
- **引导修复**：针对 🔴 问题，给出具体的 `/pg_fix` 命令建议

---

## 第〇步：前置状态检查（必须先于一切执行）

读取 `spec-status.json`，根据当前阶段做判断：

| `currentPhase` | 处理方式 |
|---|---|
| `开发中` 且 `codeProgress.completedFiles < totalFiles` | ⚠️ 产码未完成，输出警告，询问是否继续 |
| `开发中` 且产码已全部完成 | 正常执行 review |
| `验证中` / `技术设计` / `任务拆分` | 正常执行 review |
| 阶段早于 `技术设计`（如 PRD生成、澄清中） | ❌ 拒绝执行，提示先完成设计 |

**产码未完成时，必须输出以下提示并等待用户明确确认：**

```
⚠️ 检测到产码尚未完成！

当前进度：[completedFiles]/[totalFiles] 个文件
已完成：[completedList]
未完成：[待产出文件列表]

对未完成的代码执行 Code Review 可能导致遗漏问题。

→ 输入「继续」— 对已产出的代码进行部分 review
→ 输入「取消」— 返回，继续执行 `/pg_code` 完成产码
→ 输入 `/pg_code` — 立即跳转继续产码
```

**只有用户明确输入「继续」后，才进入下一步执行 review。**

## 第一步：加载审查基准

### 1.1 加载设计文档
1. 读取 `spec-status.json`，获取 `files.design` 指向的程序设计文档
2. 读取「涉及文件清单」中所有已产出文件的代码内容
3. 若无设计文档，仅基于代码质量规范进行审查

### 1.2 检索项目规范（必须执行）

在执行 Review 之前，**主动扫描项目中是否存在以下类型的规范文档**：

**查找路径（按优先级）**：
- `docs/` / `doc/` / `wiki/` / `.github/` 等文档目录下的规范类文件
- 文件名包含「规范」「约定」「guide」「convention」「style」「standard」「best-practice」等关键词的 Markdown/文本文件
- 项目根目录的 `CONTRIBUTING.md`、`CODING_GUIDE.md`、`STYLE_GUIDE.md` 等

**同时查找项目中的优秀代码示例**：
- 在同包/相邻包中寻找与被审查文件**同类型**的已有实现（Controller / Service / Mapper）
- 重点关注：命名风格、注解使用习惯、异常处理套路、日志打印方式、分页写法等

**检索结果处理**：

| 检索结果 | 处理方式 |
|---|---|
| 找到规范文档 | 提取关键规则，作为「维度6：代码规范」的**项目特定基准**，优先级高于通用规则 |
| 找到同类代码示例 | 将其命名/结构/注解风格作为参照，对被审查代码做风格一致性检查 |
| 均未找到 | 使用内置规范审查，同时**额外检查代码质量**：是否有清晰的设计模式、合理分层、消除重复；在报告中注明「未找到项目规范文档」并指出所有屎山堆积/设计缺陷 |

## 第二步：执行七维度 Code Review

### 维度 1：设计符合性
- 接口路径/方法/参数是否与程序设计文档（第5章）一致
- 服务层核心逻辑是否与设计文档（第6章）描述一致
- 数据模型字段是否与设计（第4章）一致
- Apollo 配置项是否按设计实现

> 💡 **PRD 层面的完整验收（功能点覆盖、验收标准逐条检查）不在 Review 范围内**，由 `/pg_verify` 负责。
> Review 只需发现代码逻辑**明显违背设计文档描述**的情况并标注 🔴。

### 维度 2：代码质量
- 方法是否过长（建议单方法 ≤ 50 行）
- 是否有重复代码（相似逻辑超过 3 次应提取）
- 是否有魔法值（硬编码的数字/字符串应提取为常量）
- 是否有无效的注释或过时的 TODO

### 维度 3：异常与健壮性
- 所有外部调用是否有异常处理
- 空指针风险：是否对可能为 null 的对象做了防御
- 参数校验：接口入参是否有必要的校验（@NotNull / @Valid 等）
- 事务边界：是否有遗漏的事务声明，或不必要的大事务

### 维度 4：并发与性能

**后端项目：**
- 是否有线程安全问题（共享变量、静态可变状态）
- 循环内是否有数据库查询（N+1 问题）
- 是否有合理的缓存策略（重复读的数据是否缓存）
- CompletableFuture 使用是否正确（异常处理、线程池配置）

**前端项目：**
- 列表渲染是否使用应有的 key，是否避免使用 index 作为 key
- 是否存在内存泄漏（事件监听器未在 unmount 时移除）
- 频繁更新的数据是否已做防抖/节流处理
- 大量数据渲染是否有分页或虚拟滚动方案

### 维度 5：安全性

**后端项目：**
- 接口是否做了权限校验（是否需要登录态验证）
- 数据库查询是否防 SQL 注入（是否使用了参数化查询）
- 敏感信息是否有脱敏处理（手机号、身份证、密码等）
- 返回数据中是否有不应暴露的字段

**前端项目：**
- 用户输入是否有 XSS 过滤（禁止直接 innerHTML 输入用户内容）
- Token/权限信息是否安全存储（避免存 localStorage 且无加密）
- 敏感接口请求是否都通过 HTTPS
- 请求参数是否有过滤/校验，防止前端传入非法参数

### 维度 6：代码规范
- 注释是否为简体中文，描述是否清晰

**后端项目：**
- public 方法是否有 Javadoc 注释
- Import 是否规范（无通配符 `*`，顺序正确）

**前端项目：**
- 关键函数/组件是否有中文说明注释，包含需求名称、修改时间、核心逻辑
- 组件/函数命名是否语义清晰，明确表达其职责
- 是否有残留的 `console.log` 调试代码未清除

**通用项目：**
- 命名/结构/注解是否与项目中同类优秀代码的风格一致（基于第一步检索结果）
- 若找到项目规范文档，逐条核对其中的强制性要求

### 维度 7：跨文件一致性（必须全量扫描）

> 这是逐文件审查发现不了的问题。大模型在不同文件中对同一个概念用了不同的表达，编译不报错但逻辑错误，且很难查。

**必须横扫所有产出文件，检查以下四类不一致：**

| 检查类型 | 具体检查点 | 严重级 |
|---|---|---|
| **枚举值/常量命名** | 同一个状态/类型在不同文件中是否用相同的枚举常量（如：ServiceA 用 `Status.ENABLE` 而 ServiceB 用整数 `1`） | 🔴 |
| **字段名对齐** | 同一业务字段在 DTO/VO/DO 中的命名是否一致（如：`createTime` vs `createdAt` vs `gmtCreate`） | 🟡 |
| **错误码统一** | 不同 Controller/Service 抛出的异常，使用的错误码是否统一源（如：错误码应使用项目规范的 BizException） | 🔴 |
| **接口参数一致性** | 同一字段在请求和响应中的类型是否匹配（如：请求里传字符串， Service 里按 Long 解析） | 🔴 |

**横扫方法：**
1. 提取所有产出文件中的枚举类名 + 字段名 + 错误码清单
2. 两两比对，找出命名相同但实现不同的条目，以及命名不同但意义相同的条目
3. 对对应设计文档第 2 章「涉及文件清单」中的说明，确认所有文件使用的是同一套术语体系

> ⚠️ 维度 7 必须在审查完所有单个文件后才执行（需要全量文件上下文）。若只审查了部分文件，必须标注「本维度仅对已审查文件有效」。

## 特殊场景

### 指定只 Review 某个文件：
```
/pg_review XxxService.java      → 只审查指定文件
/pg_review --security           → 只进行安全维度审查
/pg_review --perf               → 只进行并发/性能维度审查
```

### 上下文自愈（无 spec-status.json 时）：
若未找到 `spec-status.json`，不报错，改为：
1. 要求用户提供需要 Review 的文件路径或文件内容
2. 仅基于代码质量规范进行审查（跳过设计符合性验证维度）
3. 提示：「如需对照设计文档审查，请先执行 `/pg_plan` 生成设计文档」

---

## 禁止行为

- ❌ 禁止在审查过程中自动修改任何代码
- ❌ 禁止以"整体代码质量较好"等模糊结论替代具体问题
- ❌ 禁止漏过 🔴 安全类问题（必须全量报出）
- ❌ **禁止跳过维度 7**：只要仪出了多个文件，必须执行跨文件一致性完整扫描（即使单文件审查指令也需自动扫描跨文件引用关系）
