---
description: PG - 验证命令 - 对照程序设计文档验证代码实现的完整性与一致性，输出结构化验证报告（✅/⚠️/❌） (PG Code Verification Command)
---

当用户输入 `/pg_verify` 命令时，你必须严格按照以下步骤执行：

---

## 验证规范（内嵌）

- **只验证，不修改**：发现问题只报告，不自动修改代码或文档
- **对照设计文档**：以程序设计文档为唯一验证基准
- **结构化输出**：验证结果分类（✅ 通过 / ⚠️ 待确认 / ❌ 不符合）
- **有问题必须引导**：针对每个 ❌ 或 ⚠️ 项，给出具体修复命令建议

---

## 执行步骤

### 第〇步：前置状态检查（必须先于一切执行）

读取 `spec-status.json`，根据当前阶段做判断：

| `currentPhase` | 处理方式 |
|---|---|
| `开发中` 且产码**未完成** | ⚠️ 输出警告，询问是否继续 |
| `开发中` 且产码**已完成** / `验证中` | 正常执行 |
| 阶段早于 `开发中`（PRD生成/澄清/技术设计/任务拆分）| ❌ 拒绝执行，提示先完成产码 |

**产码未完成时，输出以下提示并等待明确确认：**

```
⚠️ 产码尚未完成，当前进度 [completedFiles]/[totalFiles]！

对不完整的代码进行验证，会产生误报（文件不存在等）。

→ 输入「继续」— 对已产出代码进行部分验证
→ 输入「取消」— 返回，先执行 `/pg_code` 完成产码
```

---

### 第一步：加载验证基准文档

1. 读取 `spec-status.json`，获取以下两个基准文档：
   - `files.design` 指向的**程序设计文档**（主要基准）
   - `files.prd` 指向的 **PRD**（兆底基准）
2. 从程序设计文档提取：
   - 第2章：涉及文件清单
   - 第5章： API 接口设计
   - 第6章：服务层核心逻辑
   - 第4章：数据模型变更
3. 从 PRD 提取：
   - 功能清单（各功能点和评收标准）
   - 接口字段定义和业务规则
4. **若未找到程序设计文档：**
   ```
   ⚠️ 未找到程序设计文档，请提供（任选一种）：
   1. 文件路径
   2. 直接粘贴程序设计文档全文
   ```

### 第二步：执行五维度验证

#### 维度 1：文件完整性
对照「涉及文件清单」确认每个文件是否存在：
- ✅ 已创建 / ✅ 已修改 / ❌ 未找到

#### 维度 2：API 接口一致性
- 接口路径是否与设计一致
- 请求参数字段名、类型是否匹配
- 响应结构是否符合设计
- 是否向后兼容

#### 维度 3：服务层逻辑
- 核心业务路径是否与设计一致
- 并发/幂等/事务边界是否按设计处理
- 异常处理路径是否覆盖设计描述的场景

#### 维度 4：数据模型
- 新增/修改字段是否与设计一致（字段名、类型、默认值）
- DO 类字段变更是否完整

#### 维度 5：文档一致性
- 代码变更是否与程序设计文档保持同步
- 若有接口变更，文档中的接口章节是否已更新

#### 维度 6：✨ PRD 验收标准兆底验证

> 这是最终安全网：确保代码完成了**用户真正想要的功能**，而不只是「按安设计文档要求做到了就隶了」

**若 `files.prd` 存在，必须执行本维度；不存在则标注「未提供 PRD，跳过本维度」。**

小分类验证：
- **功能点覆盖**： PRD 功能清单中的每个功能点，是否均已在代码中实现
- **验收标准覆盖**： PRD 中每条验收标准（可测试条件）是否已在代码中实现
- **接口字段层**： PRD 要求的接口字段定义，与实际代码中的 VO/DTO/Controller 是否一致
- **业务规则层**： PRD 中的关键业务规则（如状态流转条件、计算公式），是否在 Service 层正确实现

### 第三步：输出结构化验证报告

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🔍 验证报告 — [需求名称]
验证时间：YYYY-MM-DD HH:mm
基准文档：[程序设计文档路径] + [PRD 路径或「未提供」]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## 📁 文件完整性
✅ XxxController.java — 已创建
❌ XxxService.java — 未找到（设计要求新增）

## 🔌 API 接口一致性
✅ POST /api/xxx/create — 路径、参数均符合设计
⚠️ GET /api/xxx/list — 响应字段 total 缺失

## ⚙️ 服务层逻辑
✅ 并发场景使用 CompletableFuture — 符合设计
⚠️ 幂等处理：设计要求 requestId 去重，未见实现

## 🗄️ 数据模型
✅ 新增字段 source_type — 已在 DO 类中添加

## 📝 文档一致性
✅ 代码实现与设计文档一致

## ✨ PRD 验收兆底
[若 files.prd 不存在，此节输出「未提供 PRD，跳过」]
✅ 功能点「[PRD功能名]」— 代码已实现
❌ 验收标准「[PRD中的验收条件]」— 代码中未见实现
⚠️ 接口字段「[PRD要求的字段]」— 已实现但字段名不直观

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
验证结论：
✅ 通过：[N] 项
⚠️ 待确认：[N] 项
❌ 不符合：[N] 项（其中 PRD 不符：[N] 项）

📌 待处理项目：
1. ❌ XxxService.java 未创建 → `/pg_code` 补充产出该文件
2. ⚠️ list 接口缺失 total 字段 → `/pg_fix 在 list 接口响应中补充 total 字段`
3. [PRD 不符项] ❌ PRD 验收条件「[...]」未实现 → `/pg_fix [具体修复描述]`
   或 → `/pg_edit 清键 PRD，[该功能点]已变更，删除此验收条件`
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 第四步：根据结论引导下一步

| 验证结果 | 引导行为 |
|---|---|
| 全部 ✅ 通过 | 提示可使用 `/pg_done` 进行需求收尾 |
| 有 ⚠️ 待确认 | 列出待确认项，询问用户如何处理 |
| 有 ❌ 不符合（来自设计文档） | 明确告知必须修复，给出 `/pg_fix` 建议，**不允许继续 `/pg_done`** |
| 有 ❌ 不符合（来自 PRD） | **必须先判断原因**： |
| | &nbsp;&nbsp;① 代码确实漏实了 → `/pg_fix` 修复代码 |
| | &nbsp;&nbsp;② PRD 功能已调整/删除 → `/pg_edit` 清键 PRD 中该功能点 |
| | &nbsp;&nbsp;③ 已知明提前明确放弃 → 在 PRD 中标注「本期不实现」 |

---

## 特殊场景

### 指定验证维度
```
/pg_verify api     → 只验证接口一致性
/pg_verify files   → 只验证文件完整性
/pg_verify logic   → 只验证服务层逻辑
/pg_verify docs    → 只验证文档一致性
```

### `/pg_fix` 后触发 `/pg_verify`
聚焦在本次修改涉及的文件和维度进行验证，而非全量验证。

---

## 禁止行为

- ❌ 禁止在验证过程中自动修改任何代码或文档
- ❌ 禁止忽略 ❌ 不符合项直接引导用户 `/pg_done`
- ❌ 禁止模糊报告（如"基本符合"），必须明确标注每项状态
