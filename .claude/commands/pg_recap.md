当用户输入 `/pg_recap` 命令时，你必须严格按照以下步骤执行：

> ⚠️ 本命令的知识写入步骤**必须将内容写入实体文件**，不得仅在回复中展示而不写文件。

---

## 前置：确定 Knowledge Base 路径

Knowledge Base 存储在**当前项目根目录**下的 `pg/knowledge/` 目录，随项目代码一起维护，不同项目之间的知识互相独立。

**项目根目录识别方式（按优先级依次尝试）**：
1. 当前工作区（Workspace）的根目录
2. 执行 `git rev-parse --show-toplevel` 获取 git 仓库根目录
3. 若均无法确定，询问用户：「请告知你的项目根目录路径」

**Knowledge Base 完整路径**：`{项目根目录}/pg/knowledge/`

包含以下 6 个分类文件：

```
pg/knowledge/
├── business_terms.md     # 📚 业务术语
├── system_arch.md        # 🏗️ 系统架构
├── data_rules.md         # 📊 数据规则
├── platform_specs.md     # 🌐 平台特性
├── team_process.md       # ⚙️ 团队约定
└── domain_logic.md       # 💡 业务逻辑
```

**首次使用时**：若 `pg/knowledge/` 目录不存在，在第三步写入前自动创建并初始化 6 个空分类文件。

---

## 第一步：扫描会话，萃取关键变量

扫描本次会话的完整对话历史，识别用户引入的**关键业务变量**。

**关键变量的判断标准**（满足以下任一即纳入）：
- 用户解释了一个词/概念的特定含义（业务黑话、缩写、领域术语）
- 用户描述了某个系统/服务的上下游关系或调用链
- 用户纠正了 AI 对某字段、枚举值、规则的错误理解
- 用户说明了某平台/环境的特有行为或限制
- 用户补充了团队内部约定、分工规则、不成文规范
- 用户提供了某功能的边界条件、判断规则、例外处理

**排除以下内容**（不属于知识变量）：
- 纯代码实现细节（具体的类名、方法体）
- 临时调试信息或一次性数据
- 已经是业界通用的技术术语（无需特殊解释的）

对每条萃取出的知识，自动判断所属分类：

| 分类文件 | 图标 | 判断依据 |
|---|---|---|
| `business_terms` | 📚 | 一个词/短语有特定含义，不是通用行业术语 |
| `system_arch` | 🏗️ | 涉及服务调用链、模块归属、系统边界 |
| `data_rules` | 📊 | 字段含义、枚举值语义、null/0 区别、计算逻辑 |
| `platform_specs` | 🌐 | 特定平台（Hema/Meituan/等）的独特行为或规则 |
| `team_process` | ⚙️ | 人员分工、流程规范、不成文规定 |
| `domain_logic` | 💡 | 具体功能的判断规则、边界条件、例外处理 |

## 第二步：输出萃取结果，等待用户确认

以编号列表格式输出所有萃取的知识条目，**不得添加任何额外解释**，保持输出极度简洁：

```
📋 本次会话知识萃取（共 N 条）

[1] 📚 业务术语   | [知识条目一句话概括]
[2] 🏗️ 系统架构   | [知识条目一句话概括]
[3] 📊 数据规则   | [知识条目一句话概括]
[4] 🌐 平台特性   | [知识条目一句话概括]
[5] ⚙️ 团队约定   | [知识条目一句话概括]
[6] 💡 业务逻辑   | [知识条目一句话概括]

---
请输入采纳项编号（如：1,3,5 或 all 或 none）：
```

> ⚠️ 若本次会话未发现任何关键业务变量，输出：「本次会话未发现可沉淀的业务知识，暂无内容可保存。」并结束流程。

---

## 第三步：接收用户确认，写入 Knowledge Base

### 3.1 解析用户输入

- `all` → 采纳全部条目
- `none` → 不采纳任何条目，结束流程
- `1,3,5` → 仅采纳编号 1、3、5 的条目

### 3.2 初始化（首次使用）

若 `{项目根目录}/pg/knowledge/` 目录不存在，先创建目录并初始化以下 6 个文件：

```markdown
# [分类全称] 知识库

> 最后更新：— | 条目数：0

---
```

分类全称对照：

| 文件名 | 全称 |
|---|---|
| `business_terms.md` | 📚 业务术语 |
| `system_arch.md` | 🏗️ 系统架构 |
| `data_rules.md` | 📊 数据规则 |
| `platform_specs.md` | 🌐 平台特性 |
| `team_process.md` | ⚙️ 团队约定 |
| `domain_logic.md` | 💡 业务逻辑 |

### 3.3 写入规则（增量更新，非新建）

对每条采纳的知识条目：

**步骤 A**：读取对应分类文件。

**步骤 B**：检查文件中是否已存在**同名/同义**条目：
- 若**已存在**：更新该条目的定义，在"来源会话"字段追加当前会话 ID 和日期（不覆盖历史记录）
- 若**不存在**：在文件末尾追加新条目

**步骤 C**：更新文件顶部的「最后更新」时间和「条目数」。

**每条知识条目的写入格式**：

```markdown
## [条目标题]

**定义**：[完整的定义描述，可多句]
**来源会话**：[conversationId 前8位] / [YYYY-MM-DD]
**使用场景**：[在什么业务场景下需要了解这个知识]

---
```

---

## 第四步：输出保存结果

写入完成后输出简洁的结果报告（**不重复展示知识内容**）：

```
✅ 知识已保存完成（共 N 条）

📚 业务术语   → [条目名称1]、[条目名称2]
🏗️ 系统架构   → [条目名称3]
📊 数据规则   → [条目名称4]

📁 Knowledge Base：{项目根目录}/pg/knowledge/

---
下次开始新任务时，可使用 /pg_recall 召回相关知识。
```

---

## 禁止行为

- ❌ 禁止将知识库写到项目目录以外的任何固定路径（如 ~/.gemini/antigravity/knowledge/）
- ❌ 禁止萃取纯代码实现细节（具体类名、SQL 语句等）
- ❌ 禁止在输出萃取列表时添加冗余解释（保持 token 极简）
- ❌ 禁止在保存结果中重复展示知识条目的完整内容
- ❌ 禁止每次都新建 KI 文件，必须增量追加到现有分类文件
- ❌ 禁止用户回复 `none` 时仍然写入任何文件
