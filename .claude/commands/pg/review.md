---
description: PG - 代码审查命令 - 产码完成后对照设计文档和代码质量规范进行 Code Review，输出审查清单与改进建议 (PG Code Review Command)
---

当用户输入 `/pg:review` 命令时，你必须严格按照以下步骤执行：

---

## Code Review 规范（内嵌）

- **只审查，不修改**：发现问题只输出建议，不自动改代码
- **分层审查**：按接口层 → 业务层 → 数据层逐层检查
- **结构化输出**：每个问题标注严重等级（🔴 必须修复 / 🟡 建议修改 / 🟢 可选优化）
- **引导修复**：针对 🔴 问题，给出具体的 `/pg:fix` 命令建议

---

## 第〇步：前置状态检查（必须先于一切执行）

读取 `spec-status.json`，根据当前阶段做判断：

| `currentPhase` | 处理方式 |
|---|---|
| `开发中` 且 `codeProgress.completedFiles < totalFiles` | ⚠️ 产码未完成，输出警告，询问是否继续 |
| `开发中` 且产码已全部完成 | 正常执行 review |
| `验证中` / `技术设计` / `任务拆分` | 正常执行 review |
| 阶段早于 `技术设计`（如 PRD生成、澄清中） | ❌ 拒绝执行，提示先完成设计 |

**产码未完成时，必须输出以下提示并等待用户明确确认：**

```
⚠️ 检测到产码尚未完成！

当前进度：[completedFiles]/[totalFiles] 个文件
已完成：[completedList]
未完成：[待产出文件列表]

对未完成的代码执行 Code Review 可能导致遗漏问题。

→ 输入「继续」— 对已产出的代码进行部分 review
→ 输入「取消」— 返回，继续执行 `/pg:code` 完成产码
→ 输入 `/pg:code` — 立即跳转继续产码
```

**只有用户明确输入「继续」后，才进入下一步执行 review。**

---

## 第一步：加载审查基准

1. 读取 `spec-status.json`，获取 `files.design` 指向的程序设计文档
2. 读取"涉及文件清单"中所有已产出文件的代码内容
3. 若无设计文档，仅基于代码质量规范进行审查

---

## 第二步：执行六维度 Code Review

### 维度 1：设计符合性
- 接口路径/方法/参数是否与 API 接口设计一致
- 服务层核心逻辑是否与设计文档描述一致
- 数据模型字段是否与设计一致
- Apollo 配置项是否按设计实现
- **✨ PRD 兜底**（若 `files.prd` 存在则必须执行）：
  - PRD 功能清单中的每个功能点，是否均已实现
  - PRD 每条验收标准（可测试条件），是否在代码中有对应实现
  - PRD 接口字段定义，与实际 VO/DTO/Controller 是否一致
  - PRD 关键业务规则（状态流转/计算逻辑），是否在 Service 层正确落地
  - **若 PRD 与代码有出入，必须判断原因并标注**：
    - `🔴 [PRD不符] 代码漏实现` → `/pg:fix`
    - `🟡 [PRD变更] PRD 该功能已调整，代码正确` → `/pg:edit` 修正 PRD
    - `🟡 [本期放弃] 已明确不实现` → `/pg:edit` 在 PRD 中标注「本期不实现」

### 维度 2：代码质量
- 方法是否过长（建议单方法 ≤ 50 行）
- 是否有重复代码（相似逻辑超过 3 次应提取）
- 是否有魔法值（硬编码的数字/字符串应提取为常量）
- 是否有无效的注释或过时的 TODO

### 维度 3：异常与健壮性
- 所有外部调用是否有异常处理
- 空指针风险：是否对可能为 null 的对象做了防御
- 参数校验：接口入参是否有必要的校验（@NotNull / @Valid 等）
- 事务边界：是否有遗漏的事务声明，或不必要的大事务

### 维度 4：并发与性能
- 是否有线程安全问题（共享变量、静态可变状态）
- 循环内是否有数据库查询（N+1 问题）
- 是否有合理的缓存策略（重复读的数据是否缓存）
- CompletableFuture 使用是否正确（异常处理、线程池配置）

### 维度 5：安全性
- 接口是否做了权限校验（是否需要登录态验证）
- 数据库查询是否防 SQL 注入（是否使用了参数化查询）
- 敏感信息是否有脱敏处理（手机号、身份证、密码等）
- 返回数据中是否有不应暴露的字段

### 维度 6：代码规范
- 注释是否为简体中文，描述是否清晰
- public 方法是否有 Javadoc 注释
- Import 是否规范（无通配符 *，顺序正确）
- 命名是否符合项目的命名惯例（参考已有系统的命名风格）

## 第四步：根据结论引导下一步

### 有 🔴 必须修复项：
```

逐项处理建议：
1. 🔴 [安全] 接口缺少权限校验 → `/pg:fix 在 XxxController.create 方法添加权限校验`
2. 🔴 [并发] 幂等风险 → `/pg:fix 实现 requestId 幂等控制`

修复完成后，建议再次执行 `/pg:review` 复核，或直接 `/pg:verify` 验证整体实现。
```


## 特殊场景

### 指定只 Review 某个文件：
```
/pg:review XxxService.java      → 只审查指定文件
/pg:review --security           → 只进行安全维度审查
/pg:review --perf               → 只进行并发/性能维度审查
```

### 上下文自愈（无 spec-status.json 时）：
若未找到 `spec-status.json`，不报错，改为：
1. 要求用户提供需要 Review 的文件路径或文件内容
2. 仅基于代码质量规范进行审查（跳过设计符合性验证维度）
3. 提示：「如需对照设计文档审查，请先执行 `/pg:plan` 生成设计文档」

---

## 禁止行为

- ❌ 禁止在审查过程中自动修改任何代码
- ❌ 禁止以"整体代码质量较好"等模糊结论替代具体问题
- ❌ 禁止漏过 🔴 安全类问题（必须全量报出）
