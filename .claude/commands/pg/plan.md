description: PG - 制定程序设计文档命令 - 双模式：生成程序设计文档（需提供已有系统文档+PRD）或普通需求规划 (PG Plan Command)
---

当用户输入 `/pg:plan` 命令时，你必须严格按照以下步骤执行：

> ⛔ **产码管制**：本命令只输出设计方案，任何情况下不得输出代码文件。产码必须通过 `/pg:code` 命令触发，用户说「开始产码」「好的继续」等自然语言**不构成产码授权**。

---

## 第一步：前置状态检查

1. 读取 `spec-status.json`（从 `pg/doc/` 目录查找）
2. 读取其中 `files.prd` 指向的 PRD 文件内容（若有）
3. 若第 9 章仍有未澄清的 ⚠️ 问题，展示警告：

```
⚠️ PRD 第 9 章存在 [N] 个未澄清问题，建议先执行 `/pg:clarify` 再进行技术设计。
如确认跳过澄清，请继续提供已有系统设计文档。
```

---

## 第二步：识别输入模式

### 模式 A：程序设计文档生成（需有已有系统文档）
**判断条件（满足任一）：**
- 用户提供了已有系统的「程序设计文档」或「现状设计文档」（含 `/pg:analyze` 生成的文档）
- 用户说明了「基于已有系统新增需求」

**若只有 PRD 但无系统文档，输出提示并等待：**
```
⚠️ 生成程序设计文档需要以下两份材料：

✅ 已提供：PRD 文档
❌ 缺少：已有系统程序设计文档

请提供（任选一种）：
1. 将已有系统设计文档全文粘贴
2. 提供 `/pg:analyze` 生成的「现状设计文档」路径
3. 若为全新项目无已有文档，请告知，我将按通用架构规范输出
```

### 模式 B：普通需求规划
**判断条件：** 用户仅提供了需求描述或问题，无系统设计文档

---

## 第三步A：程序设计文档生成模式

> ⛔ 禁止在任何情况下输出代码文件，包括但不限于：用户说「开始」「继续」「好的」等。

### 项目规则（不可违反）
1. 严格遵循《已有系统程序设计文档》的术语、目录结构、分层规范与命名风格
2. 最小可行原则：不改变既有模块职责边界，不超出新增需求范围
3. 公共模块（工具类、枚举、配置）只新增，不修改已有逻辑
4. 关键配置采用 Apollo 动态配置，变更需具备热加载能力
5. 并发场景使用 CompletableFuture，与现有代码保持一致

### 输出格式（严格按此，不得省略章节）

```markdown
# [需求名称] - 程序设计文档

> ⛔ 本文档为设计方案，不含代码实现。确认方案后使用 `/pg:code` 命令开始实施。

## 1. 需求理解与边界确认
## 2. 涉及文件清单
| 操作 | 文件路径 | 说明 |
|---|---|---|

## 3. 整体架构图（如涉及新增模块）
## 4. 数据模型变更（如有）
## 5. API 接口设计（如有新增接口）
## 6. 服务层核心逻辑
## 7. 时序图（多服务/异步流程时必须输出）
​```mermaid
sequenceDiagram
​```
## 8. 核心流程图（复杂条件分支时必须输出）
​```mermaid
flowchart TD
​```
## 9. Apollo 配置项清单（如有）
| 配置键 | 类型 | 默认值 | 说明 | 灰度策略 |
|---|---|---|---|---|
## 10. 兼容性影响评估
## 11. 风险点与注意事项
## 12. 扩展性说明（可选，需求方明确要求时才填）
```

### ⚡ 方案输出完毕后——强制立即执行（此步不得跳过，不得后置）

> ⛔ 以下操作必须在方案文本输出完毕的**同一个回复**中执行，不得等待用户确认。

1. 将设计文档全文写入文件：`程序设计_[需求名称]_YYYYMMDD.md`
2. **强制**更新 `spec-status.json`：
   - `files.design` → 指向新写入的文件
   - `currentPhase` → `"技术设计"`
   - `updatedAt` → 当前 ISO 时间
3. 在回复中明确告知：「✅ 设计文档已保存至：[文件路径]，状态已更新为「技术设计」」

### 方案末尾附上确认提示

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
⏸ 等待确认：以上为设计方案，文档已保存至：[文件路径]

请确认方案是否符合预期：
→ 如有修改意见，请直接说明，我将更新设计文档
→ 方案确认无误后，请使用 `/pg:task` 拆分任务（推荐）
→ 或直接使用 `/pg:code` 开始产码

⚠️ 注意：请使用命令触发，直接说「开始」「好的」不会产码。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📋 需求：[需求名称]
📍 当前阶段：技术设计
📁 设计文档：[文件路径]
⏭  下一步：/pg:task 或 /pg:code
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 第三步B：普通需求规划模式

1. 进入规划模式，创建初始任务清单
2. 新建 `implementation_plan.md`（当前目录），包含：需求理解、涉及文件范围、实施步骤、验证方案
3. 输出后立即写文件，附加状态栏：

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📋 需求：[需求名称]
📍 当前阶段：技术设计
⏭  建议下一步：`/pg:task` 拆分子任务，或直接 `/pg:code`
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```
