---
description: PG - 任务拆分命令 - 将程序设计文档拆解为可执行子任务清单，完成后引导 /pg_code (PG Task Decomposition Command)
---

当用户输入 `/pg_task` 命令时，你必须强制对程序设计文档进行极细粒度的任务拆解。

---

## 执行步骤

### 1. 读取程序设计文档
- 读取 `spec-status.json`，获取 `files.design` 指向的设计文档
- 若不存在，读取 `implementation_plan.md`
- 若均不存在，提示用户先执行 `/pg_plan`

### 2. 强制进入规划状态
创建或更新任务清单文件，基于设计文档中的「涉及文件清单」进行拆分。

### 3. 拆分规则（极细粒度）

每个子任务必须满足：
- **3~5 次工具调用内可完成**（例如：创建一个文件、修改一处逻辑）
- **有明确的完成标志**（如：文件已创建、方法已实现）
- **与其他子任务解耦**（尽量可独立验证）

**推荐拆分维度（按文件逐一拆分）：**
```
- [ ] 新增 XxxController.java — 实现 POST /xxx/create 接口
- [ ] 新增 XxxService.java — 实现 doCreate() 核心逻辑
- [ ] 修改 ApolloConfig.java — 新增 xxx.enable 配置项
- [ ] 新增 XxxDO.java — 定义数据模型（若有数据库变更）
- [ ] 新增 XxxMapper.java + XxxMapper.xml — 数据访问层
```

### 4. 工时估算（必须执行）

在拆分完成后，为每个子任务给出工时估算：

**估算粒度说明：**
| 复杂度 | 描述 | 参考工时 |
|---|---|---|
| 简单 | 仅新增字段、添加配置项、简单 CRUD | 0.5h ~ 1h |
| 中等 | 新增完整接口（含 Controller/Service/Mapper）| 2h ~ 4h |
| 复杂 | 涉及复杂业务逻辑、并发控制、多服务联动 | 4h ~ 8h |
| 很复杂 | 需要重构、设计评审或大量联调 | 8h+ |

**工时估算时考虑因素：**
- 接口联调时间（前后端联调：+1h/接口）
- 单元测试时间（若需编写：+0.5h/类）
- Code Review 修改时间（经验值：+0.5~1h）
- 历史包袱风险（若来自 /pg_analyze 发现了高风险技术债：+50%）

### 5. 写入任务清单文件（立即执行，不等用户确认）

将拆分好的任务清单写入 `[specDir]/task.md`（若无 spec-status.json 则写到当前目录）：
- **立即**更新 `spec-status.json`：
  - `currentPhase: "任务拆分"`
  - `files.task: "task.md"`
  - 初始化 `codeProgress: { totalFiles: N, completedFiles: 0, currentFile: null, completedList: [] }`

### 6. 输出任务清单（含工时）并等待确认

输出格式为**含工时列的表格**：

```
📋 任务清单已生成，共 [N] 个子任务：

| 序号 | 状态 | 任务 | 操作 | 复杂度 | 预估工时 |
|---|---|---|---|---|---|
| 1 | [ ] | 新增 XxxController.java | 新增 | 中等 | 2h |
| 2 | [ ] | 新增 XxxService.java | 新增 | 复杂 | 4h |
| 3 | [ ] | 修改 ApolloConfig.java | 修改 | 简单 | 0.5h |
| 4 | [ ] | 新增 XxxDO + XxxMapper | 新增 | 中等 | 1.5h |

⏱ 总预估工时：[汇总] 小时
（含联调/Review 缓冲约 [N]h，建议排期 [日期范围] 完成）

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📋 需求：[需求名称]
📍 当前阶段：开发中
⏭  下一步：`/pg_code` 开始按任务清单逐文件产码
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

确认任务清单和工时估算无误后，请使用 `/pg_code` 命令开始产码。

> ⚠️ **注意**：请使用 `/pg_code` 命令触发，直接说「开始」「好的」等自然语言**不会开始产码**。

如需调整拆分或工时，请直接说明。
```

---

## 注意事项

- 遇到业务架构不确定的任务，先向用户确认再拆分
- 不安排需要数十步才能闭环的超大任务
- 优先级：核心业务逻辑 > 接口层 > 配置层 > 工具类
