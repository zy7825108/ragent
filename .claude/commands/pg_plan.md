---
description: PG - 制定程序设计文档命令 - 自动识别前端/后端项目，生成对应的技术设计方案；前端项目额外标注后端 API 依赖（PG Plan Command）
---

当用户输入 `/pg_plan` 命令时，你必须严格按照以下步骤执行：

> ⛔ **产码管制**：本命令只输出设计方案，任何情况下不得输出代码文件。产码必须通过 `/pg_code` 命令触发，用户说「开始产码」「好的继续」等自然语言**不构成产码授权**。

---

## 第零步：项目类型识别（强制，最先执行）

扫描当前工作区根目录，判断项目类型：

| 判断依据 | 项目类型 |
|---|---|
| 存在 `pom.xml` / `build.gradle` / `src/main/java/` | **后端项目** |
| 存在 `package.json` / `vue.config.js` / `vite.config.*` / `.vue` / `.tsx` 文件 | **前端项目** |
| 无法判断 | 询问用户：「请确认当前是前端项目还是后端项目？」 |

> 识别结果会影响第三步A 的设计文档结构，其余步骤前后端完全一致。

---

## 第一步：前置状态检查

1. 读取 `spec-status.json`（从 `pg/doc/` 目录查找）
2. 读取其中 `files.prd` 指向的 PRD 文件内容（若有）
3. 若第 9 章仍有未澄清的 ⚠️ 问题，展示警告：

```
⚠️ PRD 第 9 章存在 [N] 个未澄清问题，建议先执行 `/pg_clarify` 再进行技术设计。
如确认跳过澄清，请继续提供已有系统设计文档。
```

---

## 第二步：识别输入模式

### 模式 A：程序设计文档生成（需有已有系统文档）
**判断条件（满足任一）：**
- 用户提供了已有系统的「程序设计文档」或「现状设计文档」（含 `/pg_analyze` 生成的文档）
- 用户说明了「基于已有系统新增需求」

**若只有 PRD 但无系统文档，输出提示并等待：**
```
⚠️ 生成程序设计文档需要以下两份材料：

✅ 已提供：PRD 文档
❌ 缺少：已有系统程序设计文档

请提供（任选一种）：
1. 将已有系统设计文档全文粘贴
2. 提供 `/pg_analyze` 生成的「现状设计文档」路径
3. 若为全新项目无已有文档，请告知，我将按通用架构规范输出
```

### 模式 B：普通需求规划
**判断条件：** 用户仅提供了需求描述或问题，无系统设计文档

---

## 第三步A：程序设计文档生成模式

> ⛔ 禁止在任何情况下输出代码文件，包括但不限于：用户说「开始」「继续」「好的」等。

### 后端项目规则（不可违反）
1. 严格遵循《已有系统程序设计文档》的术语、目录结构、分层规范与命名风格
2. 最小可行原则：不改变既有模块职责边界，不超出新增需求范围
3. 公共模块（工具类、枚举、配置）只新增，不修改已有逻辑
4. 关键配置采用 Apollo 动态配置，变更需具备热加载能力
5. 并发场景使用 CompletableFuture，与现有代码保持一致

### 前端项目规则（不可违反）
1. 严格遵循《已有系统程序设计文档》的命名风格、目录结构与组件规范
2. 最小可行原则：不改变既有模块职责边界，不超出新增需求范围
3. 公共模块（公共组件、全局样式、工具函数、接口封装）只新增，不修改已有逻辑
4. 新增代码兼容项目当前运行环境，优先使用项目已引入的库，不新增不必要依赖
5. 异步场景与现有代码保持一致（Promise/async-await）

### 输出格式

**后端项目**（严格按此，不得省略章节）：

```markdown
# [需求名称] - 程序设计文档

> ⛔ 本文档为设计方案，不含代码实现。确认方案后使用 `/pg_code` 命令开始实施。

## 1. 需求理解与边界确认
## 2. 涉及文件清单
| 操作 | 文件路径 | 说明 |
|---|---|---|

## 3. 整体架构图（如涉及新增模块）
## 4. 数据模型变更（如有）
## 5. API 接口设计（如有新增接口）
## 6. 服务层核心逻辑
## 7. 时序图（多服务/异步流程时必须输出）
​```mermaid
sequenceDiagram
​```
## 8. 核心流程图（复杂条件分支时必须输出）
​```mermaid
flowchart TD
​```
## 9. Apollo 配置项清单（如有）
| 配置键 | 类型 | 默认值 | 说明 | 灰度策略 |
|---|---|---|---|---|
## 10. 兼容性影响评估
## 11. 风险点与注意事项
## 12. 扩展性说明（可选，需求方明确要求时才填）
```

**前端项目**（在后端格式基础上做以下调整）：

- 第 5 章「API 接口设计」改为：**「接口对接设计」**，说明前端调用的接口（现有接口/新增接口）及字段映射
- 第 6 章「服务层核心逻辑」改为：**「页面/组件核心逻辑」**，说明组件结构、状态管理、交互流程
- **新增第 13 章（强制）：「后端 API 依赖」**，见下方说明
- **新增第 14 章：「前端开发约束」**，见下方说明

---

### 📋 前端专属：第 13 章「后端 API 依赖」（强制输出）

> 前端设计方案必须明确：哪些接口是当前后端系统**还没有提供、需要后端配合新开发的**。

```markdown
## 13. 后端 API 依赖

### 现有接口（直接复用，无需后端改动）
| 接口路径 | 用途 | 字段映射说明 |
|---|---|---|

### 需要后端新增/修改的接口（⚠️ 需协调后端同学）
| 接口路径 | 变更类型 | 需新增/修改的字段/逻辑 | 优先级 |
|---|---|---|---|

> 若本次需求完全依赖现有接口，此章节填写「无新增后端依赖」。
```

---

### 📋 前端专属：第 14 章「前端开发约束」

```markdown
## 14. 前端开发约束

- **最少修改原则**：仅修改绝对必要的代码/样式/配置，不做无关联的重构或格式调整
- **公共模块禁忌**：公共组件/全局样式/工具函数/接口封装，禁止直接修改，必须通过新增实现
- **兼容性**：新增代码需兼容项目当前运行环境，优先使用项目已引入的库
- **可追溯性**：修改/新增代码必须添加注释（需求名称、修改时间、核心逻辑说明）
```

---

### ⚡ 方案输出完毕后——强制立即执行（此步不得跳过，不得后置）

> ⛔ 以下操作必须在方案文本输出完毕的**同一个回复**中执行，不得等待用户确认。

1. 将设计文档全文写入文件：`程序设计_[需求名称]_YYYYMMDD.md`
2. **强制**更新 `spec-status.json`：
   - `files.design` → 指向新写入的文件
   - `currentPhase` → `"技术设计"`
   - `updatedAt` → 当前 ISO 时间
3. 在回复中明确告知：「✅ 设计文档已保存至：[文件路径]，状态已更新为「技术设计」」

### 方案末尾附上确认提示

```

⏸ 等待确认：以上为设计方案，文档已保存至：[文件路径]

请确认方案是否符合预期：
→ 如有修改意见，请直接说明，我将更新设计文档
→ 方案确认无误后，请使用 `/pg_task` 拆分任务（推荐）
→ 或直接使用 `/pg_code` 开始产码

⚠️ 注意：请使用命令触发，直接说「开始」「好的」不会产码。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📋 需求：[需求名称]

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 第三步B：普通需求规划模式

1. 进入规划模式，创建初始任务清单
2. 新建 `implementation_plan.md`（当前目录），包含：需求理解、涉及文件范围、实施步骤、验证方案
3. 输出后立即写文件，附加状态栏：

```

📋 需求：[需求名称]
📍 当前阶段：技术设计
⏭  建议下一步：`/pg_task` 拆分子任务，或直接 `/pg_code`
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```
