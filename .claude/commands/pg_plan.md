## 第零步：项目类型识别（强制，最先执行）

扫描当前工作区根目录，判断项目类型：

| 判断依据 | 项目类型 |
|---|---|
| 存在 `pom.xml` / `build.gradle` / `src/main/java/` | **后端项目** |
| 存在 `package.json` / `vue.config.js` / `vite.config.*` / `.vue` / `.tsx` 文件 | **前端项目** |
| 无法判断 | 询问用户：「请确认当前是前端项目还是后端项目？」 |

> 识别结果会影响第三步A 的设计文档结构，其余步骤前后端完全一致。

## 第一点五步：🔍 自动知识召回（强制，不得跳过）

> 知识库里存着这个项目历次需求沉淀的业务词汇、设计决策和历史约定。在进入设计之前先将这些知识注入当前会话，可以直接充充「已理解」列表，并大幅减少「不知道」的提问量。

**执行逐项（不得略过任何一项）：**

### 1. 确定知识库路径

按以下优先级定位：
1. `spec-status.json` 中的 `projectRoot` 字段 → `{projectRoot}/pg/knowledge/`
2. 当前工作区根目录 `pg/knowledge/`
3. `git rev-parse --show-toplevel`，再拼 `pg/knowledge/`

若路径不存在或目录为空：静默跳过，不输出任何内容，直接进入第二步。

### 2. 读取知识库文件

逐一读取以下六个分类文件（文件不存在则跳过）：
```
pg/knowledge/
├── business_terms.md     # 📚 业务术语
├── system_arch.md        # 🏗️ 系统架构
├── data_rules.md         # 📊 数据规则
├── platform_specs.md     # 🌐 平台特性
├── team_process.md       # ⚙️ 团队约定
└── domain_logic.md       # 💡 业务逻辑
```

### 3. 基于需求内容做关键词匹配

提取 PRD 中的业务关键词（需求名称、功能名、涉及模块名、接口名等），与知识库条目的「索引词 / 标题 / 定义」做语义匹配。

匹配策略（按优先级）：
1. 条目标题或索引词直接包含需求关键词
2. 条目的「场景」或「是什么」与需求高度匹配
3. 条目属于本需求涉及模块的典型场景

只输出「明确相关」的条目，宁少不错。

### 4. 输出召回结果

**情况 A：找到匹配知识**

在进入第二步之前，在回复中输出（Markdown 格式）：

```
🔍 已从知识库召回 [N] 条相关知识，将作为下方「已理解」的依据源自动注入当前会话：

• [条目名1]：[一句话摘要]
• [条目名2]：[一句话摘要]
```

> 召回结果展示完毕后，自动将全部命中条目作为本次设计的隐性上下文前提。在后续理解确认门的 ✅ 已理解列表中，直接将这些知识作为已知上下文列入（标注来源为「知识库」），不得再次列入为 ❓ 问题。

**情况 B：知识库为空 / 无匹配条目**

静默跳过，不输出任何内容，直接进入第二步。

## 第二点五步：⛔ 理解确认门（强制，不得跳过）

> ⛔ **本步骤是输出设计文档的前置门控**，必须在分析完所有输入材料后、输出任何设计内容之前执行。

读取完 PRD、现状设计文档等所有材料后，**必须先输出以下三分法清单，等待用户确认后才能继续出设计文档**：

```
## 🧠 进入设计前——请确认我的理解

> 以下是我在阅读 PRD 和现状文档后整理的认知清单。
> 请逐类检查：✅ 类确认即可，⚠️ 类有误请直接纠正，❓ 类必须提供答案我才能继续。

### ✅ 我已理解的（有明确的文档依据）
- [理解1]：依据来自 [PRD第X章 / 现状设计文档第X章 / 接口定义]
- [理解2]：...

### ⚠️ 我的假设（无明确资料，基于经验推断，需你确认）
- 假设1：[具体假设内容]——请确认是否符合你们的实际情况
- 假设2：...

### ❓ 我不知道的（信息完全缺失，必须你补充我才能继续设计）
- 问题1：[具体问题，说明为什么需要这个信息]
- 问题2：...
```

**三类内容的处理规则（不得违反）：**

| 类型 | 规则 |
|---|---|
| ✅ 已理解 | 供用户快速校验，发现有误时用户可直接纠正 |
| ⚠️ 我的假设 | **等待用户逐条确认或纠正**，用户确认「没问题」后继续；有纠正则重新理解再列清单 |
| ❓ 我不知道 | **强阻塞**：有任何一条未回答，不得输出设计文档，必须持续追问直到全部答完 |

**❓ 类必须主动挖掘以下场景（遇到就必须列入）：**
1. **业务领域术语**：文档中出现了我不确定含义的词汇（如：「一致性校验」到底校验什么？）
2. **数据口径**：某字段的来源、计算方式或取值范围不明确
3. **调用关系**：需要调用某个下游服务/接口，但文档中未说明具体是哪个
4. **业务规则例外**：主流程之外的边界处理方式未说明（如：失败时是否重试？重试几次？）
5. **历史约定**：可能存在团队约定或历史原因，但文档没有记录的部分
6. **外部依赖存在性**：设计中需要调用某个 RPC 服务/方法/接口，我是基于命名规律推断其名称的，并非文档明确指定

> ❗ **第 6 条必须标注为 ⚠️ 假设，不得列入 ✅ 已理解**：
> - ✅ 已理解 = 文档里明确写了这个接口/方法的具体名称
> - ⚠️ 假设 = 我根据命名规律/上下文推断这个名字应该是这样的
>
> 命名推断错误会导致产码时调用了不存在的方法，编译报错且无法定位。


> ⚠️ 若所有内容均有明确依据（✅ 类非空，⚠️ 和 ❓ 均为空），则直接告知「无待确认问题，准备输出设计文档」并继续。

**⚠️ 答案确认后立即回写（不得等到 `/pg_archive`）：**

用户回答了 ❓ 类问题 / 纠正了 ⚠️ 类假设后，**立即执行以下回写动作，不得延迟**：

| 答案类型 | 回写目标 | 回写位置 |
|---|---|---|
| 业务术语定义 | 现状设计文档 | 未尾「## 附录：业务术语表」（不存则新建） |
| 数据口径说明 | 现状设计文档 | 第 6 章数据设计对应字段备注列 |
| 调用关系补充 | 现状设计文档 | 第 7 章集成与接口 |
| 业务规则例外 | 现状设计文档 | 第 3 章核心业务逻辑设计对应规则项下 |
| 历史约定 | 现状设计文档 | 未尾「## 附录：历史约定与注意事项」（不存则新建） |

> 若现状设计文档不存在：将答案追加到 `spec-status.json` 的 `knowledgeNotes` 字段（数组格式），供 `pg_archive` 第七步使用。

## 第三步A：程序设计文档生成模式

> ⛔ 禁止在任何情况下输出代码文件，包括但不限于：用户说「开始」「继续」「好的」等。

### 后端项目规则（不可违反）
1. 严格遵循《已有系统程序设计文档》的术语、目录结构、分层规范与命名风格
2. 最小可行原则：不改变既有模块职责边界，不超出新增需求范围
3. 公共模块（工具类、枚举、配置）只新增，不修改已有逻辑
4. 关键配置采用 Apollo 动态配置，变更需具备热加载能力
5. 并发场景使用 CompletableFuture，与现有代码保持一致
6. **最简实现自检（输出设计文档前必须执行）**：检查以下三项，若任一为"是"，必须在设计文档第12章中说明理由，否则删除该设计：
   - 引入了新的设计模式/抽象接口，但用一个普通类就能实现？
   - 引入了项目中尚未使用的新依赖/新框架？
   - 设计了可扩展点，但 PRD 中没有任何扩展需求？

### 前端项目规则（不可违反）
1. 严格遵循《已有系统程序设计文档》的命名风格、目录结构与组件规范
2. 最小可行原则：不改变既有模块职责边界，不超出新增需求范围
3. 公共模块（公共组件、全局样式、工具函数、接口封装）只新增，不修改已有逻辑
4. 新增代码兼容项目当前运行环境，优先使用项目已引入的库，不新增不必要依赖
5. 异步场景与现有代码保持一致（Promise/async-await）
6. **最简实现自检（输出设计文档前必须执行）**：检查以下两项，若任一为"是"，必须在设计文档第12章说明理由：
   - 新增了 npm 依赖，但项目现有库已能满足需求？
   - 设计了通用组件，但当前 PRD 只有一个使用场景？

### 接口调用方影响
