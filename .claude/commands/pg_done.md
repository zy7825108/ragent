---
description: PG - 需求收尾命令 - 汇总所有产物、生成稳定性 Checklist、标记需求完成 (PG Done Command)
---

当用户输入 `/pg_done` 命令时，你必须严格按照以下步骤执行：

> ⚠️ 本命令会生成实体文件，**文件生成后必须立即写入磁盘**，不得仅在回复中展示而不写文件。

---

## 第一步：前置检查

读取 `spec-status.json`，检查以下条件：

| 条件 | 状态 | 处理方式 |
|---|---|---|
| `files.prd` 不为空 | ✅/❌ | ❌ 停止，提示先执行 `/pg_prd` |
| `files.design` 不为空 | ✅/❌ | ❌ 停止，提示先执行 `/pg_plan` |
| `task.md` 中无 `[ ]` 未完成项 | ✅/⚠️ | ⚠️ 列出未完成项，询问是否继续 |
| 最近执行过 `/pg_verify` 且无 ❌ | ✅/⚠️ | ⚠️ 提醒但不强制阻止，询问确认 |

**若 task.md 中仍有未完成任务，输出（Markdown 格式，非代码块）：**

⚠️ task.md 中仍有 [N] 个未完成子任务：
- [ ] XxxService.java 产码
- [ ] ApolloConfig.java 修改

请选择：
→ 回复「继续」— 忽略未完成项，强制收尾
→ 回复「取消」— 先完成剩余任务

---

## 第二步：生成并写入收尾报告

> ⚡ **立即写文件**：生成 `收尾报告_[需求名称]_YYYYMMDD.md`，写入 `[specDir]` 目录。

报告内容（Markdown 格式）：

```markdown
# [需求名称] 收尾报告

> 生成时间：YYYY-MM-DD HH:mm
> 需求归档目录：[specDir]

## 产物汇总

| 产物类型 | 文件名 | 最后更新 |
|---|---|---|
| PRD 文档 | [files.prd] | [updatedAt] |
| 程序设计文档 | [files.design] | [updatedAt] |
| 澄清记录 | [files.clarify 或「无」] | — |
| 任务清单 | [files.task] | — |
| 稳定性 Checklist | [files.checklist] | — |

## 变更摘要

[基于 task.md 中已完成项目，一句话描述本次需求的核心变更]

## 涉及文件清单

[从程序设计文档第 2 章复制完整文件清单]
```

写入完成后立即告知：
> ✅ 收尾报告已写入：`[文件路径]`

同时更新 `spec-status.json`：
- `files.report` → 指向收尾报告文件
- `updatedAt` → 当前时间

---

## 第三步：检查文档与代码同步状态

快速检查代码实现与程序设计文档的一致性：
- 若有未同步内容，明确指出并提示：「建议先执行 `/pg_edit` 同步后再完成收尾」
- 若完全同步，继续下一步

---

## 第四步：生成并写入稳定性上线 Checklist

> ⚡ **立即写文件**：生成 `上线Checklist_[需求名称]_YYYYMMDD.md`，写入 `[specDir]` 目录。

**根据本次需求实际涉及的模块动态生成，只输出涉及的章节，不输出无关章节。**

> ⚠️ **每个维度必须包含两层内容**：
> 1. **检查项**：逐条勾选（`[ ]` / `[x]`）
> 2. **📝 明细**：根据设计文档和代码**自动填入真实数据**（DDL/接口列表/文件清单/回滚方案等），**禁止留空占位符或写「待填写」**

文件内容（Markdown 格式）：

```markdown
# [需求名称] 稳定性上线 Checklist

> 生成时间：YYYY-MM-DD HH:mm
> **上线前请逐项确认，完成后在 [ ] 中打 ✅**

---

## 一、代码稳定性

- [ ] Code Review 已完成（`/pg_review` 无 🔴 必须修复项）
- [ ] 代码验证已通过（`/pg_verify` 无 ❌ 不符合项）
- [ ] **后端项目**：所有 public 方法有中文 Javadoc 注释
- [ ] **前端项目**：关键函数/组件有中文说明注释，无残留调试 `console.log`
- [ ] 无硬编码的魔法値（已提取为常量或配置）
- [ ] 边界条件已处理（null 値、空列表、越界等）
- [ ] 异常均有明确的捕获和处理逻辑

📝 **本次涉及文件明细**（从设计文档「涉及文件清单」章节逐行提取）：
| 文件路径 | 操作 | 核心改动说明 |
|---|---|---|
| [com/example/XxxService.java] | 新增/修改/删除 | [一句话说明此文件的核心改动] |

---

## 二、数据稳定性

[仅当后端项目且本次需求有数据库变更时输出此章节]

- [ ] DDL 脚本（建表/加字段/加索引）已在**测试环境**执行并验证
- [ ] 新增字段有合理默认值（存量数据不受影响）
- [ ] 数据迁移脚本已准备并在测试环境验证
- [ ] **回滚 SQL 已准备**（知道出问题怎么还原数据）
- [ ] 大表 DDL 操作已评估锁表风险（如需 gh-ost / pt-osc 执行）
- [ ] 索引已根据实际查询场景设计（非全量冗余索引）

📝 **DDL 变更明细**（从设计文档「数据模型」章节提取，填入可执行 SQL）：
```sql
-- 本次实际 DDL 变更（可直接在生产执行）
ALTER TABLE xxx ADD COLUMN yyy VARCHAR(64) DEFAULT '' COMMENT 'zzz说明';
CREATE INDEX idx_yyy ON xxx(yyy);
```

📝 **回滚 SQL**（必填，出问题时直接复制执行，与上方 DDL 一一对应）：
```sql
ALTER TABLE xxx DROP COLUMN yyy;
DROP INDEX idx_yyy ON xxx;
```

## 三、接口稳定性

[仅当本次需求有接口变更或新增时输出此章节]

- [ ] 新增接口已做入参校验（@NotNull / @Valid 等）
- [ ] 修改接口向后兼容（未删除/改名历史字段）
- [ ] 接口响应错误码统一（使用项目规范的 BizException）
- [ ] 若接口有破坏性变更：已通知所有调用方并确认联调通过
- [ ] 接口文档（YAPI/Swagger）已同步更新

📝 **接口变更明细**（从设计文档「API 设计」章节提取）：
| 接口路径 | 方法 | 类型 | 变更说明 | 向后兼容 |
|---|---|---|---|---|
| `/api/xxx/create` | POST | 新增 | [一句话描述功能] | — |
| `/api/xxx/detail` | GET | 修改 | [新增了哪个字段] | ✅ 兼容 |

## 三点五、前端构建与部署稳定性

[仅前端项目输出此章节；后端项目忽略]

- [ ] 构建产物已核查（`npm run build` 无报错/警告、无残留 `console.log`）
- [ ] 新增组件/样式未影响其他页面（局部化验证）
- [ ] 环境变量/配置已在测试环境验证生效
- [ ] 跨浏览器兼容性已验证（项目目标浏览器版本）
- [ ] 后端有新增/修改接口时：已完成联调并验证返回数据符合预期
- [ ] CDN/静态资源已处理刷新（如有）

📝 **前端构建产物明细**：
| 产物类型 | 目标路径 | 备注 |
|---|---|---|
| 新增组件文件 | [src/components/XxxNew.vue] | [一句话说明改动] |
| 修改的页面文件 | [src/views/YyyPage.vue] | [一句话说明改动] |

## 四、配置稳定性

[仅当后端项目且本次需求有 Apollo 配置项变更时输出此章节]

- [ ] 新增 Apollo 配置项已在**测试环境**验证生效
- [ ] 配置项有合理默认值（服务启动不依赖配置是否推送）
- [ ] 灰度配置项的灰度顺序和范围已明确（先内部 → 金丝雀 → 全量）
- [ ] 紧急关闭开关已就位（出问题可一键关闭功能）

📝 **配置项明细**（从设计文档「配置项」章节提取）：
| 配置 Key | 类型 | 默认值 | 说明 | 是否为开关 |
|---|---|---|---|---|
| `xxx.feature.enable` | Boolean | false | [控制哪个功能的开关] | ✅ 是 |

## 五、并发与事务稳定性

[仅当后端项目且本次需求涉及并发写或事务操作时输出此章节]

- [ ] 核心写操作已实现幂等（requestId / 唯一键 / 状态判断）
- [ ] 事务边界已明确（@Transactional 最小化，避免大事务）
- [ ] 分布式锁/乐观锁已在并发场景正确使用
- [ ] 锁粒度合理（避免全表锁或过粗粒度锁）
- [ ] 并发测试场景已覆盖（多线程下数据一致性验证）

📝 **并发/事务明细**：
| 并发场景描述 | 处理方式 | 涉及方法 | 测试结论 |
|---|---|---|---|
| [描述并发写入的业务场景] | 乐观锁/分布式锁/幂等Key | `XxxService.doCreate()` | [测试通过/待测试] |

## 六、缓存稳定性

[仅当本次需求涉及缓存读写时输出此章节]

- [ ] 缓存雪崩防护已就位（过期时间随机抖动）
- [ ] 缓存与 DB 数据一致性已验证

📝 **缓存 Key 明细**：

|---|---|---|---|

## 七、消息队列稳定性

[仅当本次需求涉及 MQ 生产或消费时输出此章节]

- [ ] 消费失败已配置重试策略（最大重试次数 / 死信队列）
- [ ] 消息生产失败有兜底处理（事务消息 / 本地消息表）
- [ ] 消息体字段变更向后兼容（消费方可处理旧格式）
- [ ] 消费 TPS 已评估，不超过下游服务承载能力

📝 **消息队列明细**：

|---|---|---|---|---|

## 八、监控与应急

- [ ] 关键业务指标已有监控（成功率、处理量、转化率等）
- [ ] 关键技术指标已有监控（接口 P99 响应时间、错误率、JVM GC）
- [ ] 告警规则已配置（异常触发时及时通知到值班群）
- [ ] **回滚方案已明确**（开关/代码/数据三步回滚路径已文档化）
- [ ] 上线后 30 分钟拨测计划已就绪

📝 **回滚方案**（必填，出问题时按顺序执行，无需思考直接操作）：

| 第二步（代码回滚） | `git revert [commit-hash]` 后重新打包部署 | ~10 分钟 |
| 第三步（数据回滚） | 若有数据变更，执行本 Checklist 第二章「回滚 SQL」 | 视数据量 |

📝 **上线后 30 分钟拨测清单**：

## 九、上线后验证（上线后 30 分钟内执行）

- [ ] 拨测关键接口，返回结果符合预期（见上方拨测清单）
- [ ] 查看错误日志，无新增异常（对比上线前基线）
- [ ] 核心功能 P0 用例快速回归（手工或自动化）

- [ ] 若有灰度：确认灰度流量功能表现符合预期后再扩量

## 禁止行为

- ❌ 禁止只在回复中展示而不写文件（收尾报告和 Checklist 必须写入实体文件）
- ❌ **禁止将 Commit Message 写入文件**（只在回复中展示）
- ❌ 禁止自动执行 `git commit`
- ❌ 当存在 `/pg_verify` ❌ 不符合项时，禁止允许收尾
- ❌ Checklist 中与本次需求无关的章节**必须省略**，不得全量输出
